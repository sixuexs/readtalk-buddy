## 1. 模块定位与设计背景

### 1.1 重构前的问题

原提升计划页的功能为:展示五维均分与成长曲线、一段 LLM 生成的提升建议文本、一个可勾选的周目标清单。存在以下问题:

| 环节 | 原状 | 问题 |
|---|---|---|
| 诊断 | 五维平均分 + 百字评语 | 粒度过粗,无法定位具体差距(如"共情倾听 62 分"无法说明缺少哪类行为) |
| 计划 | 200 字以内纯文本 | 不可执行、不可验证、不可追溯 |
| 任务 | 字符串列表 + 布尔勾选 | 勾选无门槛、无记录、无反馈 |
| 闭环 | 无 | 计划不影响训练内容;训练结果不回写任务进度 |
| 周期 | 无真实周概念 | 无周起止、无历史、无跨周对比 |
| 缺陷 | 评分事件触发 `assessAbility()` 重新生成周目标并清空勾选状态 | 用户每完成一次训练,已勾选进度即丢失 |

### 1.2 设计目标与约束

目标:将模块从"评估报告展示"升级为"训练闭环系统",链路为:

**统计聚合 → 诊断(可下钻) → 周训练计划(结构化任务) → 针对性训练 → 完成验证 → 周期总结**

四条设计约束:

1. **可追溯**:每个子技能分数都能下钻到用户原话证据(原文片段、问题说明、改进示范)。
2. **可验证**:应用内训练任务由评分数据自动判定完成;真实场景任务必须提交文字记录并经 AI 依据标准判定。不提供无验证的手动勾选。
3. **计划驱动训练**:周计划决定下一次训练的主题、角色与练习重点;训练角色的 system prompt 注入配合指令;评分输出练习重点的前后对比。
4. **统计与计划生成解耦**:评分事件只触发规则计算(统计刷新、任务进度),不触发 LLM 计划生成;计划仅在周切换或用户手动操作时生成。此约束同时修复 1.1 中的勾选重置缺陷。

## 3. 子技能模型与证据

### 3.1 子技能词典(16 项)

五维之下细分 16 项可观察子技能。词典为常量类 `com.backend.constant.SubSkillConstants`(唯一参数源,含定义、可观察信号、评分判据、推荐训练映射、阈值常量);前端镜像 `frontend/src/constants/subSkills.ts`(仅 key/中文名/所属维度)。短名 snake_case,发布后冻结。

| 短名 | 名称 | 所属维度 | 定义 | 可观察信号 | 评分判据 |
|---|---|---|---|---|---|
| `filler_control` | 填充词控制 | clarity | 减少"那个/就是说/嗯/呃"等停顿填充 | 填充词密度(每百字,<3 不扣,口径同 B 文档) | 90+ 几乎无填充;70-89 偶发不影响;40-69 明显口头禅;<40 密集 |
| `point_first` | 观点先行 | clarity | 先给结论再展开 | 发言首句是否含明确观点句 | 按发言轮次中观点先行的占比 |
| `concrete_wording` | 用词具体 | clarity | 用具体名词/事例替代空泛表述 | 空泛词("东西/挺好/差不多")密度与具体细节 | 有无实例、细节、量化表述 |
| `claim_evidence` | 观点-论据配对 | logicality | 每个主张有支撑 | 主张句后是否跟随"因为/比如/数据"等支撑 | 配对率 + 论据实质性(防空壳,同 B 文档防刷分原则) |
| `structure_linking` | 结构连接 | logicality | 有效使用先后/因果连接组织多句 | 有效连接词使用(区别于堆叠"然后",仲裁同 B §2-5) | 结构完整度 |
| `self_consistency` | 前后自洽 | logicality | 观点前后不矛盾 | 跨轮次观点比对 | 有无自我推翻/矛盾 |
| `emotion_naming` | 情绪命名 | empathy_listening | 识别并说出对方情绪 | "听起来你有点…"类句式且指向对方 | 命中且准确计正向;套话不加分 |
| `paraphrase` | 复述确认 | empathy_listening | 用自己的话复述对方观点再推进 | "你的意思是…?/所以说你…" | 复述准确且带延展计正向;空洞附和不计(B §2 仲裁) |
| `empathic_followup` | 共情追问 | empathy_listening | 追问指向对方内在体验 | 问感受/原因/经历类问题(话题推动类提问归 interactivity) | 追问深度与对方回应质量 |
| `active_questioning` | 主动提问 | interactivity | 用问题推动对话 | 征询性提问频次与质量(语义过滤,问号不直接计分) | 被动应答与主动发起的比例 |
| `topic_driving` | 话题推动 | interactivity | 主动开启/延展新话题 | 新话题发起次数、接话延展率 | 冷场后是否主动续接 |
| `turn_giving` | 发言权让渡 | interactivity | 把发言机会交给对方 | 邀请式结尾("你觉得呢")、发言占比均衡 | 独白 >80% 且无邀请记低分(同 B) |
| `silence_handling` | 冷场处理 | interactivity | 对话停滞时的化解动作 | 对方短回复/停滞后,是否换角度、自嘲或提问 | 化解成功率 |
| `less_hedging` | 减少道歉退缩词 | relaxation | 少用"可能我不对/随便说说/不好意思"铺垫 | 退缩/道歉词密度(每百字 <2 不扣);道歉词只计入本项(B §2-3 仲裁) | 有观点直接表达 |
| `self_disclosure` | 自我表露 | relaxation | 主动分享个人经历/感受 | 第一人称经历句、感受句占比 | 纯附和/纯沉默记低分(B 防刷分) |
| `non_defensive` | 被质疑不防御 | relaxation | 面对异议时解释而非反击或收回 | 对方质疑后:坚持并论证记高;反击或立即收回记低 | 需出现质疑轮次才可评,否则输出 null |

**样本约束**:本场对话无观察机会的子技能输出 null(不强制打分);聚合均值跳过 null;含分场次 < 2(`MIN_SAMPLES`)的子技能不参与诊断与计划生成,前端置灰并提示所需场次。

**阈值与窗口常量**(集中于 `SubSkillConstants`):聚合窗口 `RECENT_SESSIONS=10`;自动判定达标分 `AUTO_MIN_SCORE=70`;徽章阈值 `MASTERY_L1=80`/`MASTERY_L2=90`;证据上限 `EVIDENCE_MAX=4`;引文截断 `QUOTE_MAX_LEN=60`。

### 3.2 评分输出扩展

`SimulationService.scoreConversation` 保持单次 LLM 调用,输出 JSON 在原有字段上追加:

```json
{
  "clarity": 72, "...": "五维与总分、评语、标签(原有字段不变)",

  "subScores": {
    "filler_control": 80, "emotion_naming": 35, "silence_handling": null,
    "...": "16 个键全部存在,值为 0-100 整数或 null(null=本场无观察机会)"
  },
  "evidence": [
    {
      "subSkill": "emotion_naming",
      "messageOrder": 12,
      "quote": "用户原话逐字片段(≤60 字)",
      "issue": "问题说明(结合对方上一句状态)",
      "rewrite": "改进示范(第一人称、可直接使用;negative 必填)",
      "polarity": "negative"
    }
  ]
}
```

prompt 追加段(运行文本见 `SimulationService.scoreConversation`,子技能判据段由 `SubSkillConstants.promptBlock()` 生成)的关键约束:

- 无观察机会输出 null,禁止强制打分;
- 判据服从 B 文档横切仲裁(道歉/退缩词只计入 `less_hedging`;堆叠"然后"计入 `filler_control`;空洞附和不给 `paraphrase`/`empathic_followup`/`turn_giving` 正向分);
- 某维度子技能均值与该维度分偏差超过 25 时,须在 comment 中说明主因;
- 防刷分同样适用(套话模板不计高分);
- 证据 0~4 条:低于 60 分且有观察机会的子技能至少 1 条 negative;positive 至多 1 条;`quote` 必须为用户原话逐字片段并给出 `messageOrder`。

**解析容错**(`parseSubScores`/`parseEvidence`,包级可见、有单测):子技能键白名单校验,未知键记日志;数值 clamp 到 [0,100];缺失/非数值记 null;证据坏条目丢弃、超量截断、`polarity` 缺省为 negative。子技能层任何失败不影响五维主分入库。

**运行配置**:推理型模型可能因输出预算耗尽返回空内容,评分调用在空内容时以"直接输出紧凑 JSON"指令重试一次;`deepseek.api.max-tokens` 由 4096 调整为 8192。

### 3.4 与五维评分体系的关系

- 五维分仍是唯一的整篇级权威分(B 文档口径不变),综合分 = 五维等权平均;
- 子技能是诊断粒度补充,判据不得违反 B §2 横切仲裁;
- 词典修订须同步 B 文档;短名一经发布冻结(DB/prompt/前端三方对齐)。

### 4.2 任务结构与三种完成方式

```jsonc
{
  "id": "t1",
  "type": "simulation | realworld | knowledge",
  "subSkill": "emotion_naming",
  "title": "…", "instruction": "做法指导(120 字以内,教具体步骤)",
  "successCriteria": "人类可读的完成标准",
  "verifyMode": "auto | evidence",
  "autoRule": { "kind": "session_subskill_min | focus_session_count",
                "subSkill": "…", "minScore": 70, "target": 2 },   // verifyMode=auto 时必填
  "target": 2, "progress": 0,
  "status": "pending | in_progress | done | expired",
  "submissions": [ { "text": "…", "aiFeedback": "…", "accepted": true, "at": "…" } ],
  "whyRefs": [ { "sessionId": "…", "subSkill": "…" } ],   // 任务依据的证据引用("为什么是这个任务")
  "dueAt": "…",
  "creditedSessionIds": ["…"],   // 已计入进度的会话(自动判定去重)
  "doneAt": "…"
}
```

| 类型 | 示例 | 判定方式 | 前端交互 |
|---|---|---|---|
| simulation(应用内训练) | 完成 2 场针对"情绪命名"的模拟 | auto:评分事件自动判定 | 只读进度条 + "去训练"按钮(携带练习重点直启模拟);无勾选控件 |
| realworld(真实场景) | 本周在真实对话中运用 1 次"复述确认" | evidence:提交文字记录 + AI 点评 | 提交弹层(10~200 字),展示点评结果与剩余次数 |
| knowledge(认知) | 学习做法卡并用自己的话复述要点 | evidence:同上 | 同上 |

### 4.3 生成管线(规则统计 → LLM 生成 → 校验兜底 → 持久化)

**第一步:规则统计**(`PlanStatsService.compute`,纯函数,有单测)。输入近 10 场含子技能分的会话,输出:

- `weakest`:样本 ≥2 的子技能按均值升序取前 3;
- `trending`:样本 ≥4 的子技能,按时间对半分(各至多 5 场)计算均值差,|差值| ≥5 才记录;
- `negativeEvidenceTop`:窗口内 negative 证据按子技能计数取前 3(各附最新一条原文);
- `themeGaps`:近 30 天无评分场次的模拟主题;
- `focusSubSkills`:主项 = weakest[0];若 trending 首项差值 ≤ -8 且样本 ≥3,则升为主项、weakest[0] 降为次项;否则次项 = weakest[1](均值 <70 时)。
- 无任何样本 ≥2 的子技能 → `insufficient`(前端显示解锁条件,不生成计划)。

**第二步:LLM 生成**(单次调用)。prompt 全文(`PlanService.PRESCRIPTION_PROMPT`,`{}` 为占位符):

```text
你是社交能力训练系统的训练处方专家。根据以下统计诊断，为用户生成本周训练处方。

## 统计诊断（规则引擎输出，可信）
{statsJson}

## 近期负面证据摘录（用户原话）
{negEvidence}

## 用户既有画像
总体评价：{assessment}
主要短板：{topWeaknesses}

## 生成要求
输出 3~5 个任务，严格返回 JSON：
{"summary":"≤80字，本周主攻什么、为什么（引用统计中的具体分数）",
 "tasks":[{"type":"simulation|realworld|knowledge",
           "subSkill":"子技能短名，必须出自统计诊断",
           "title":"≤25字，动词开头",
           "instruction":"≤120字，教具体做法步骤，不写空话",
           "successCriteria":"≤30字，可验证的完成标准",
           "target":1~3的整数}]}
硬约束：
1. 至少 1 个 simulation、至少 1 个 realworld，knowledge 至多 1 个；
2. simulation 任务的 subSkill 必须属于本周主攻焦点：{focusSubSkills}；
3. 同一子技能最多 2 个任务；
4. realworld 任务必须是本周内可在线下真实社交中完成、且行为可被自己观察到的；
5. target 取值：simulation 为 1~2（场次），realworld/knowledge 为 1~3（次数）。
只返回 JSON。
```

> 注:prompt 为运行文本,原样引用自代码;文中"处方/主攻"等措辞即本文档所称"周训练计划/优先改进项"。

**第三步:校验与兜底**(`assembleTasks`,有单测):逐条校验——`subSkill` 白名单(支持中文名到短名的宽容映射 `resolveKey`,联调中实测 LLM 偶发输出中文名)、类型合法、simulation 任务的子技能必须属于 focus、knowledge 至多 1 个、同一子技能至多 2 个、target clamp;不合格条目丢弃并记日志。结构兜底:缺 simulation 则按主项补一条,缺 realworld 则补一条,总数不足 3 用 `SubSkillConstants` 默认模板补齐,超过 5 截断。auto 任务自动生成 `autoRule`(kind=session_subskill_min,minScore=70);evidence 任务不设 autoRule;`whyRefs` 取统计层匹配该子技能的负面证据。

**第四步:持久化**:现存 active 计划全部置 archived(不删除,保留历史);新计划写入(status=active)。

**LLM 失败处理**:生成调用异常时,摘要与任务全部走规则模板(`fallbackSummary` + 默认任务模板),计划仍然产出;联调中本机出现间歇性 TLS 失败,该路径已实测生效。

### 4.4 触发时机与并发控制

仅三处触发,均与评分事件解耦:

1. 按需周切换(见 §6.1);
2. 手动:`POST /api/plan/regenerate`(前端确认弹窗明示"当前任务进度将归档");
3. 采纳周报草稿后的周切换实例化(见 §6.3,不调用 LLM)。

生成过程持互斥锁(`ReentrantLock.tryLock`):并发请求立即返回 `generating` 状态,前端 2 秒间隔轮询、上限 30 秒。

### 4.5 统计更新与计划生成解耦

`UserProfileTools` 拆分为两个方法:

- `refreshStats(boolean fromScoring)`:纯规则统计(五维、子技能聚合、徽章、连续天数;`fromScoring=true` 时才更新 streak,防止手动路径误重置)。评分事件调用此方法,零 LLM。
- `assessAbility()`:仅由用户手动触发,生成评估文本;周目标字段只在首次(为空时)写入,不再覆盖既有目标与勾选状态。

历史缺陷修复说明:重构前评分事件调用 `assessAbility()`,每次评分都会重新生成周目标并将勾选状态清零;解耦后该行为消除(运行时已验证:评分后勾选与附言保持不变)。

### 4.6 自动完成判定(`PlanService.onSessionScored`)

评分完成事件触发,纯规则、幂等、异常仅记日志:

```
遍历当前 active 计划中 verifyMode=auto 且 status ∈ {pending, in_progress} 的任务:
  已在 creditedSessionIds 中的会话跳过(幂等)
  kind=session_subskill_min:本场 subScores[task.subSkill] ≥ minScore → 计入
  kind=focus_session_count:本场 focusSubSkill == task.subSkill → 计入
  计入 = progress+1、记录会话 id;progress ≥ target → status=done(记 doneAt),否则 in_progress
周切换时未完成任务 → status=expired(计入周报完成度分母)
```

### 4.7 提交点评(`PlanService.submitTask`)

`POST /api/plan/tasks/{taskId}/submit {text}`,返回 `{accepted, aiFeedback, progress, status, locked, remaining}`:

1. auto 任务提交 → 拒绝并提示"由训练数据自动判定";
2. 提交次数达 3 次 → `locked=true`;
3. 文本 <10 字 → 直接拒绝(固定提示,不调用 LLM);
4. LLM 判定(prompt 全文,`PlanService.SUBMIT_PROMPT`):

```text
你是社交训练教练，正在判定用户提交的真实任务打卡是否合格。

## 任务
标题：{title}
完成标准：{successCriteria}
做法指导：{instruction}

## 用户提交的打卡内容
{text}

## 判定要求
1. 合格 = 内容包含具体事件要素（谁 / 什么情境 / 说了或做了什么 / 结果如何），且事件与任务要求的行为直接相关；
2. 纯口号或无细节（"我完成了""今天练了"）→ 不合格；
3. 事件与任务无关（如任务是"复述确认"却只写了闲聊内容）→ 不合格；
4. 宁可宽松鼓励，但底线是"能看出真的做过这个动作"。
返回 JSON：{"accepted": true或false, "aiFeedback": "≤50字，第二人称，合格时具体指出做得好的动作，不合格时给一个可操作的改进建议"}
只返回 JSON。
```

5. `accepted=true` → progress+1(达标转 done);提交记录(文本、点评、结果、时间)追加保存;
6. LLM 调用或解析失败 → 返回提示且**不计入提交次数**。

联调实测:同一任务先后提交"仅共情回应,未追问"(拒绝,指出与任务要求不符)、"追问了但缺关键词"(拒绝,给出补充方向)、"完整事件含对方原话关键词"(通过),判定与点评均符合标准。

## 5. 针对性训练(计划驱动训练)

### 5.1 参数与基线

### 5.2 角色 prompt 注入模板

运行文本(`SimulationService.coachSection`,`%s` 依次填入子技能中文名、定义、场景创设指令):

```text
【本场训练焦点】用户正在刻意练习「%s」（%s）。
你的配合要求：
1. 在对话中自然制造 2~3 次该行为的练习机会，喂球方式：%s；
2. 若进行约 6 轮后用户始终未出现该行为，可轻微引导一次（如流露更明显的情绪、直接询问看法），但绝不点破"你在练习"；
```

## 6. 周期总结与成长数据

### 6.1 周周期与按需切换

- 周口径:ISO 8601(周一为一周开始),`weekKey = 周基年-W两位周序`(`WeekKeyUtil`,含跨年单测)。
- 无定时任务。`GET /api/plan/current`、`/recommendation` 先执行 `ensureWeekRollover`:若 active 计划的 weekKey 早于当前周,依次执行——未完成任务置 expired → 生成上周周报(同周已存在则跳过,幂等)→ 计划归档 → 生成新周计划(上周周报存在已采纳草稿时直接实例化,不调用 LLM)。
- 连续训练天数(streak):自然日内有 ≥1 场评分训练记为活跃日;`refreshStats(fromScoring=true)` 中维护(昨日活跃则 +1,否则重置 1;`bestStreak` 取历史最高)。

### 6.2 周报:`weekly_reports` 集合(WeeklyReportDocument)

```jsonc
{
  "_id": "…", "userId": 1, "weekKey": "2026-W37", "planId": "…",
  "completion": { "tasksTotal": 5, "tasksDone": 0, "tasksExpired": 5,
                  "sessionsScored": 3, "focusSessions": 1,
                  "submissions": 3, "submissionsAccepted": 1 },        // 规则计算
  "deltas": { "emotion_naming": 8 },        // 本周含分场均值 − 周前窗口(≤10 场)均值;仅两侧都有分的子技能
  "highlights": [ { "sessionId": "…", "subSkill": "…", "quote": "…" } ],  // 本周 positive 证据,按子技能周均值降序、去重取 ≤2
  "aiSummary": "120 字以内(LLM)",
  "nextWeekDraft": { "summary": "…", "tasks": [ /* 与周计划任务同构,经同一校验器 */ ] },
  "adopted": false,
  "adoptedDraft": null,                     // 采纳时冻结的草稿快照
  "createdAt": "…"
}
```

生成:完成度、变化量、证据摘录全部规则计算;LLM 仅生成 `aiSummary` 与 `nextWeekDraft`(prompt 全文见 `PlanService.REPORT_PROMPT`,输入为上述规则数据)。LLM 失败时 `aiSummary` 用模板文案(引用完成数与最大提升项)、`nextWeekDraft` 置 null,周报仍然保存。

### 6.3 草稿采纳与再生成

- `POST /api/plan/reports/{weekKey}/adopt`:`adopted=true`,并将 `nextWeekDraft` 深拷贝冻结为 `adoptedDraft`(此后草稿再生成不影响已采纳内容);幂等。
- `POST /api/plan/reports/{weekKey}/draft-refresh`:按最新统计重新生成草稿(复用周计划生成的 prompt 与校验器),成功后清除 `adopted/adoptedDraft`。
- 周切换时:上周周报 `adopted=true` 且草稿任务 ≥3 → 直接实例化为新周计划(`generatedBy="adopted"`,诊断 focus 取草稿任务子技能);否则正常自动生成。

### 6.4 徽章、连续天数、维度等级

| 项 | 规则 | 存储 |
|---|---|---|
| 子技能徽章 | 近 3 场含分均值 ≥80 → Lv1(掌握);≥90 → Lv2(进阶)。按子技能 upsert:只升不降、不回收;`achievedAt` 为首次达成、`lastUpgradedAt` 为最近升级(`applyBadge` 纯函数,有边界单测) | `user_profile.badges` |
| 连续训练 | 见 §6.1 | `user_profile.streakDays/bestStreak/lastActiveDate` |
| 维度等级 | 五维均分映射:<40→Lv1、40-54→Lv2、55-69→Lv3、70-84→Lv4、≥85→Lv5(派生量不落库,前端现算) | — |
| 新徽章提示 | 前端以本地存储对比 `badges`,出现新达成时显示一次性提示条 | 前端 storage |

## 10. 已知限制与后续事项

1. **UI 人工走查未完成**:新增页面通过编译、类型检查与接口级验证,视觉与交互细节需在浏览器/微信开发者工具中人工确认。
2. **LLM 成本**:评分单次调用 token 增加约 30~50%(子技能判据 + 证据);计划、周报、点评为小上下文调用;评分事件路径零 LLM。单用户演示量级可接受,放量前需评估。
3. **子技能评分噪声**:单场样本小,均值窗口(10 场)与样本阈值(2 场)为初值,需真实数据校准;词典判据与阈值集中于 `SubSkillConstants`,调整不改结构。
4. **自动判定阈值**:`AUTO_MIN_SCORE=70` 等常量为初值;若场景创设指令过易导致虚高,调整映射表指令或阈值即可。
5. **本机环境**:对 api.deepseek.com 偶发 TLS 证书校验失败(PKIX),属环境问题;系统各 LLM 环节均有降级路径,但建议排查本机代理/证书链。
6. **单用户假设**:`/api/plan` 固定 userId=1,多用户改造时需透传(代码内已标注 TODO 位置)。
7. **旧字段兼容**:`weeklyGoals/improvementPlan` 等旧字段与接口保留只读兼容,后续版本可在确认无引用后清理。
